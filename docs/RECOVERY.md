# Lumos — Recovery Codes

How the "forgot my master password" route works, and why it is built this way.

Replaces `docs/LICENSING.md`, which documented the product-key activation gate
removed in v2.

---

## The problem

Until v2, forgetting the master password meant losing the vault permanently.
That is the correct default for a local-first password manager — but it is a
harsh one, and it is the single most common way people lose their data.

Adding any recovery route means creating a **second path to the same key**. The
only question worth arguing about is who controls that path and how strong it is.

## Approaches that were considered and rejected

These are recorded because they are the obvious ideas, and each fails for a
reason worth remembering.

**Stored facial identity.** The face template would live on the user's disk, and
the comparison would run in Lumos's own code. An attacker holding the vault file
also holds the template and the code. If matching a face releases the key, the
key must be recoverable from data already on disk — which means the vault is
decryptable without the master password. That is not a weakened vault; it is an
unencrypted one wearing a costume. (Biometric templates are also regulated
personal data in several jurisdictions.)

**A user-chosen word plus a passphrase.** Structurally the right shape, but wrong
on entropy. A user-invented word and phrase is typically far weaker than a master
password, so it becomes the new cheapest way in. An attacker stops grinding the
Argon2id-hardened password and grinds the recovery answer instead.

**A one-time ID mailed to the developer, who returns an unlock token.** Fails
both ways at once. If the token only *authorises* a reset without carrying key
material, the reset produces a working app and permanently unreadable data. If it
*can* recover the data, the developer holds a key-escrow backdoor to every user's
vault. It also does not scale past a handful of users.

## What Lumos does instead

A generated recovery code, wrapping the same cipher key that the master password
wraps. Same pattern as 1Password's Emergency Kit and Bitwarden's recovery code.

```
cipher key (random, 32 bytes, fixed for the vault's life)
   ├── wrapped by Argon2id(master password, masterSalt)
   └── wrapped by Argon2id(recovery code,   recoverySalt)
```

Either secret unwraps the cipher key. Neither can produce the other. No third
party holds either.

### The code

```
ABCDE-FGHJK-MNPQR-STVWX-YZ234-56789
```

30 characters from a 30-symbol alphabet — about **147 bits**. Generated by the
app, never chosen by the user, because a recovery secret is a second door to the
same data and must be at least as strong as the first.

- Rejection sampling, not modulo. 256 is not a multiple of 30, so `byte % 30`
  would make the first 16 symbols slightly more likely — a small but pointless
  bias in a value whose entire job is to be unguessable.
- The alphabet omits characters people confuse when copying from paper: no
  `0`/`O`, no `1`/`I`/`L`, no `U`.
- Input is normalised leniently (case, spacing, missing dashes) but **not**
  auto-corrected. Silently rewriting `O` to `0` would turn an obvious typo into a
  baffling "wrong code".

### Header format

Header format version 3 adds a `recovery` block carrying its own salt **and its
own Argon2id parameters**. It does not share the master envelope's, because
`ChangeMasterPassword` writes fresh master KDF parameters each time — if the
recovery wrap borrowed those, a future change to the KDF defaults would silently
invalidate every recovery code already in users' hands.

Each envelope's AES-GCM tag is bound to its own KDF parameters and salt as
associated data, under a different purpose string per envelope. A wrapped key is
therefore valid only in the exact header it was created for: wraps cannot be
spliced in from an older backup, and the two envelopes cannot be swapped.

## Behaviour

| Situation | What happens |
|---|---|
| New vault created | Code issued immediately, shown once |
| Existing (pre-v2) vault | Offered on the first unlock after updating; declining is allowed and re-prompts next time |
| User resets password with the code | Code stays valid — see below |
| User changes password normally | Code stays valid; it wraps the cipher key, not the password |
| User generates a new code | Previous code stops working immediately |
| Wrong code entered | Counts as a failed attempt, same backoff as passwords |
| Malformed code entered | Rejected without burning an attempt |
| No code ever set up | Master password remains the only way in; the recovery link is not shown |

**Why using a code does not consume it:** handing someone a brand-new secret to
write down at the exact moment they have just proved they lost access is the
worst possible time to do it. Regeneration is offered separately, once they are
safely back in.

**Why the database is never re-encrypted:** the cipher key does not change during
recovery or a password change — only its wrapping does. Both operations complete
instantly regardless of vault size.

## Migration from v2 headers

Vaults created before recovery existed carry a format-v2 header: master wrap
only, authenticated with a fixed AAD string.

On unlock, Lumos re-wraps under the bound AAD and rewrites the header to v3. This
is best-effort — a v2 header still unlocks perfectly well, so a failure to
rewrite never costs the user a successful unlock. It can only happen at unlock
because it needs the cipher key, which needs the master password.

Adding recovery to an existing vault leaves `vault.db` **byte-identical**. Only
the header changes.
